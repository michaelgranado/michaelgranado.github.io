Assignment 3: Performance Analysis

Problem Description:

The primary performance bottleneck in the kernelRenderCirclesTiled kernel is that every pixel thread iterates through the entire list of circles. Although a conservative tile-based culling check (circleInBoxConservative) is performed, if a circle potentially overlaps the tile associated with a thread block, all threads within that block will still load the circle's data and perform the check, even if the circle ultimately does not cover their specific pixel. This leads to a massive amount of redundant computation, particularly in scenes with a large number of circles (e.g., rand100k, rand1M, micro2M), as the workload for each pixel thread scales linearly with the number of circles potentially overlapping its tile.

Problem Reasoning:

The provided code implements a "pixel-centric" approach where each thread is responsible for calculating the final color of a single pixel. The correctness requirement mandates processing circles in a specific order for blending.

  1. Initial Observation: The test harness results show that the code is correct but extremely slow compared to the reference, especially as the number of circles increases dramatically (e.g., rand10k is ~14x slower, rand100k is ~17x slower, rand1M is ~25x slower, micro2M is ~27x slower). This suggests the algorithm's complexity scales poorly with the number of circles (`N`).
  2. Code Analysis (kernelRenderCirclesTiled): I examined the main rendering kernel. The structure is: 
    for each pixel (assigned to a thread):
  initialize pixel color
  for circleIndex from 0 to numCircles-1:
    load circle data (position, radius)
    if circleInBoxConservative(circle, pixel's tile): // Tile culling
      shadePixel(circle, pixel) // Precise check & blend
  write final pixel color
  3. Identifying Redundancy: The core issue lies in the nested loop structure combined with the culling strategy.
    • The outer loop iterates over pixels (parallelized across threads).
    • The inner loop iterates over all circles.
    • The circleInBoxConservative check prunes circles that are entirely outside the block's tile boundary. However, if a circle overlaps even a small part of the tile, every thread in that block (e.g., 256 threads) executes the check for that circle.
    • Inside shadePixel, a precise point-in-circle test is done. For a circle that only covers a few pixels within the tile, most of the 256 threads that passed the conservative check will perform this precise test only to find the pixel is outside the circle, doing no useful blending work but still incurring the overhead of the loop iteration, memory loads, and function call.
  4. Scalability Issue: The total number of inner loop iterations (before culling) is `imageWidth * imageHeight * numCircles`. The tile culling reduces this, but the work done *per pixel* still depends heavily on how many circles overlap its tile. In dense scenes (rand100k, rand1M), many circles might overlap any given tile, causing each pixel thread in that tile to iterate over a large fraction of the total circles, leading to the observed poor scaling. The work is fundamentally O(Pixels * Circles_overlapping_tile) rather than something closer to O(Pixels + Circles).

Therefore, the problem is the inefficient distribution of work: iterating through all potentially relevant circles for every single pixel, causing massive redundant checks and computation within each thread block.
