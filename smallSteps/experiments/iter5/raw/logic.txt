    <h2>Question 2</h2>
    <p>Describe the thought process you had when selecting your answer to Question 1.</p>
    <p>
        The provided CUDA code implements a pixel-parallel approach where each thread is assigned to compute the final color for a single output pixel (`kernelRenderCirclesTiled`). This inherently utilizes a high degree of parallelism, especially for large images (e.g., 1024x1024 implies over a million threads). Therefore, option (B) "Lack of parallelism" is incorrect; the code leverages massive parallelism.
    </p>
    <p>
        Option (C) "Low arithmetic intensity" refers to a low ratio of calculations to memory operations. While the shading calculation itself might not be extremely complex, the primary issue isn't necessarily the intensity of the work *per circle that covers the pixel*, but rather the sheer *amount* of work being done, much of which is unproductive.
    </p>
    <p>
        The core performance bottleneck lies in *how* the work is distributed. Each pixel thread iterates through the *entire list of circles* (`for (int circleIndex = 0; circleIndex < cuConstRendererParams.numCircles; circleIndex++)`). For scenes with many circles (like `rand1M` with 1 million circles), each of the ~1 million pixel threads performs a loop with 1 million iterations. Inside this loop, it reads circle data from global memory and performs checks. Although there's a tile-level culling (`circleInBoxConservative`), it's a coarse check. Many circles that pass the tile check still won't cover the specific pixel, leading to wasted computation and memory accesses within the `shadePixel` function's initial distance check. Furthermore, all threads within the same tile redundantly perform the same loop structure and tile-culling checks for every circle. This approach scales very poorly with the number of circles (O(pixels * circles) complexity for the checks), indicating a fundamentally inefficient assignment of work to the threads. Each thread does far more work (checking irrelevant circles) than necessary. Thus, option (A) "Inefficient assignment of work" is the most accurate description of the performance problem.
    </p>

    <h2>Question 3</h2>
    <p>Please give a detailed description of the problem that you identified in the current implementation.</p>
    <p>
        The current implementation, while correct in terms of atomicity and order preservation, suffers from severe performance issues due to its work distribution strategy within the <code>kernelRenderCirclesTiled</code> kernel. The strategy assigns one CUDA thread per pixel. Each thread is then tasked with iterating through the <strong>entire global list of circles</strong> to determine which ones contribute to its assigned pixel's final color.
    </p>
    <p>
        The main problems arising from this approach are:
    </p>
    <ol>
        <li><strong>Massive Redundant Computation:</strong> For scenes with a large number of circles (N) and pixels (P), the total number of circle checks performed across all threads approaches O(N * P). For many pixels, only a small fraction of circles actually overlap them. Therefore, each thread spends most of its time iterating through and checking circles that are irrelevant to its pixel.</li>
        <li><strong>Inefficient Culling:</strong> The code uses a conservative tile-based culling check (<code>circleInBoxConservative</code>). This helps prune circles that don't overlap the thread block's tile boundary. However, this culling is coarse. A circle might overlap the tile but still be far from a specific pixel within that tile. The thread for that pixel still needs to process the circle further (load data, call <code>shadePixel</code>) only to discard it in the finer-grained point-in-circle test inside <code>shadePixel</code>.</li>
        <li><strong>Redundant Tile Checks within a Block:</strong> All threads within the same thread block (processing pixels within the same tile) independently execute the same loop over all circles and perform the identical <code>circleInBoxConservative</code> check for each circle. This repeats the tile-culling logic unnecessarily across threads in the block.</li>
        <li><strong>Global Memory Bandwidth Consumption:</strong> In each iteration of the main loop, threads read circle properties (position, radius) from global memory. Even if a circle is quickly culled, these memory reads occur. With millions of threads iterating over millions of circles, this puts significant pressure on global memory bandwidth.</li>
        <li><strong>Poor Scaling:</strong> The computational cost scales directly with the number of circles for every pixel, regardless of the actual number of circles overlapping that pixel. This leads to the drastically poor performance observed in test cases with many circles (`rand100k`, `snowsingle`, `rand1M`, `micro2M`), where the student's time is orders of magnitude slower than the reference solution.</li>
    </ol>
    <p>
        In essence, the implementation fails to efficiently prune the set of circles that need to be considered for each pixel or group of pixels, resulting in excessive and redundant work per thread.
    </p>

    <h2>Question 4</h2>
    <p>List as many solutions as you can think of which can solve the problem you have identified in the current implementation. For each solution you list, please provide one or two sentences summarizing the key idea behind the solution.</p>
    <ul>
        <li>
            <strong>1. Tile-Based Circle Binning + Shared Memory:</strong>
            <em>Idea:</em> Pre-process the circles into per-tile lists (bins). Within the render kernel, each thread block loads its corresponding tile's circle list into shared memory, and threads only iterate over this much smaller, shared list.
        </li>
        <li>
            <strong>2. Screen-Space Subdivision (Grid/Quadtree):</strong>
            <em>Idea:</em> Build a spatial acceleration data structure (like a uniform grid or quadtree) over the screen space. Each cell/node stores a list of circles overlapping it. Pixel threads query this structure to quickly find relevant circles near them.
        </li>
        <li>
            <strong>3. Circle-Centric Processing with Per-Pixel Lists (Advanced):</strong>
            <em>Idea:</em> First, have threads associated with circles identify the pixels they cover. Then, construct per-pixel lists of relevant circles (maintaining order). Finally, have pixel threads process only the circles in their dedicated list. (Requires careful handling of list construction and ordering).
        </li>
        <li>
            <strong>4. Cooperative Tile Processing with Pre-Filtering:</strong>
            <em>Idea:</em> Similar to (1), but the pre-filtering step explicitly creates compact lists of circle indices relevant to each tile. Threads in a block cooperatively load and process only the circles from their tile's pre-filtered list, potentially using shared memory.
        </li>
         <li>
            <strong>5. Sort-Based Culling:</strong>
            <em>Idea:</em> Sort circles based on spatial position (e.g., by tile or using a Morton code). When processing a tile/pixel, leverage the sorted order to more quickly identify the range of potentially relevant circles, improving access locality and potentially enabling faster range checks.
        </li>
         <li>
            <strong>6. Optimized Data Layout:</strong>
            <em>Idea:</em> Restructure circle data (position, radius, color) in memory (e.g., structure-of-arrays vs. array-of-structures) to optimize access patterns and memory coalescing based on the chosen rendering algorithm (e.g., tile-based).
        </li>
    </ul>
