<h1>Performance Analysis of CUDA Circle Renderer</h1>

<div class="question">
  <h2>Question 1: Identifying the Performance Problem</h2>
  <p>This question is a multiple choice question, and you may only select a single option.</p>
  <div class="choices">
    <div class="choice selected-choice">A) Poor distribution of work.</div>
    <div class="choice">B) Lack of parallelism.</div>
    <div class="choice">C) Low arithmetic intensity.</div>
  </div>
  <p><strong>Selected Answer:</strong> A</p>
</div>

<div class="question">
  <h2>Question 2: Reasoning for Selection</h2>
  <div class="answer">
    <p>
      The provided CUDA code implements a pixel-parallel approach where each thread is assigned to compute the final color for a single output pixel. While this exploits parallelism across pixels, the core performance issue lies in <em>how</em> each thread determines its pixel's color.
    </p>
    <p>
      Inside the <code>kernelRenderCirclesTiled</code> kernel, every single thread iterates through the <em>entire list</em> of circles (<code>for (int circleIndex = 0; circleIndex < cuConstRendererParams.numCircles; circleIndex++)</code>). Although there's a conservative tile-based culling step (<code>circleInBoxConservative</code>), a thread assigned to a pixel must still potentially check every circle to see if it intersects the thread's tile. If it does, the thread then performs further checks (distance calculation) and potentially blending operations (<code>shadePixel</code>).
    </p>
    <p>
      This means the total computational effort scales roughly as O(NumPixels * NumCircles), before culling. For scenes with a large number of circles (like <code>rand100k</code>, <code>rand1M</code>, <code>micro2M</code>), each of the ~1 million pixel threads (for a 1024x1024 image) performs work proportional to the number of circles. Much of this work is redundant; a pixel thread iterates through and performs checks for thousands or millions of circles that are nowhere near its assigned pixel.
    </p>
    <p>
      This constitutes a "Poor distribution of work" because the work (checking circles) is not efficiently mapped to the threads. An ideal distribution would ensure threads only spend significant time processing circles that are actually relevant to their assigned pixel or region. Option B is incorrect because the code *is* parallel across pixels. Option C, Low arithmetic intensity (ratio of math operations to memory operations), is likely true for this problem and contributes to the slowness, but it's a characteristic of the computation within the loop rather than the primary reason for the *massive* amount of computation being performed. The sheer volume of redundant checks caused by the poor work distribution is the dominant bottleneck, as evidenced by the extremely high execution times for scenes with many circles.
    </p>
  </div>
</div>

<div class="question">
  <h2>Question 3: Detailed Problem Description</h2>
  <div class="answer">
    <p>
      The primary performance problem in the current <code>kernelRenderCirclesTiled</code> implementation is its brute-force, pixel-centric approach combined with inefficient work distribution. Each CUDA thread is assigned one pixel in the output image. To determine the final color of that pixel, the thread executes a loop that iterates through every single circle loaded in the scene (from <code>circleIndex = 0</code> to <code>numCircles - 1</code>).
    </p>
    <p>
      Inside this loop, for each circle, the thread performs the following steps (potentially):
    </p>
    <ol>
      <li>Reads the circle's data (position, radius) from global memory.</li>
      <li>Performs a conservative circle-in-box test (<code>circleInBoxConservative</code>) to check if the circle could possibly overlap the tile containing the thread's pixel. If not, it skips to the next circle.</li>
      <li>If the circle passes the tile test, it calculates the squared distance between the pixel center and the circle center.</li>
      <li>Compares the squared distance to the circle's squared radius to perform an exact point-in-circle test.</li>
      <li>If the pixel center is inside the circle, it calls <code>shadePixel</code>, which reads the current pixel color from global memory, performs blending calculations, and writes the updated color back to global memory.</li>
    </ol>
    <p>
      The inefficiency arises because step 1 and step 2 (and often step 3 and 4) are performed by each pixel thread for potentially <em>all</em> circles, even those geometrically distant from the pixel. Consider the <code>rand1M</code> scene with 1 million circles and a 1024x1024 image (~1 million pixels). Without any culling, this would lead to roughly 1 million * 1 million = 1 trillion iterations of the inner loop across all threads.
    </p>
    <p>
      While the <code>circleInBoxConservative</code> test prunes some work by allowing threads to skip circles that don't overlap their tile, it's insufficient for sparse scenes or scenes where many circles are large or clustered. For any circle whose bounding box overlaps a tile, <em>all</em> threads within that tile still need to read its data and perform the conservative check. Furthermore, even if a circle overlaps a tile, it might only cover a small fraction of the pixels within that tile, yet all threads in the tile perform the initial checks.
    </p>
    <p>
      This leads to massive computational redundancy. Each thread spends most of its time iterating through and rejecting circles that do not affect its pixel. This poor distribution of work—forcing every pixel thread to consider every circle—is the fundamental reason for the slow performance observed in the test harness results, where execution times increase dramatically with the number of circles. The implementation lacks an effective mechanism (like a spatial acceleration data structure) to quickly identify only the relevant circles for a given pixel or tile.
    </p>
  </div>
